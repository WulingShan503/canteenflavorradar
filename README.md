# 食堂味蕾雷达 (Canteen Flavor Radar)

基于 Agent 的高校食堂选餐系统。首届全国人工智能应用创新大赛校赛参赛作品。

针对高校食堂菜品信息不透明、学生选餐决策效率低等痛点，基于百度智能云千帆平台，
利用大模型驱动的 Agent 架构，实现从用户口味偏好输入到个性化菜品推荐的全流程智能化服务。

## 设计思路

核心是把「能不能吃」和「有多想吃」拆开：

| 层次 | 职责 | 特点 |
| --- | --- | --- |
| 偏好解析 | 自然语言 → 结构化偏好 | 大模型负责，失败时降级到关键词规则 |
| 硬性过滤 | 过敏原、忌口、饮食限制、预算上限、辣度上限 | 纯规则，结果确定可复现 |
| 排序打分 | 口味、菜系、预算、营养、口碑、便利度加权 | 纯规则，得分明细可解释 |
| 推荐语生成 | 结合菜品信息和用户原话写推荐理由 | 大模型负责，失败时用规则理由兜底 |

这样拆的原因：过敏原之类的安全约束不能交给可能产生幻觉的模型来把关，必须由确定性代码兜住；
而「为什么推荐这道菜」这类需要语感的表达，规则写出来又生硬，正好交给大模型。
模型不可用时系统降级但不瘫痪。

## 打分规则

六个维度各算出 0–1 的原始分，乘权重后累加，权重之和为 100，所以综合分天然落在 0–100。
权重按场景动态选择：

| 维度 | 默认 | 营养优先 | 热门兜底 |
| --- | --- | --- | --- |
| 口味 | 30 | 22 | 0 |
| 菜系 | 14 | 10 | 0 |
| 预算 | 16 | 14 | 10 |
| 营养 | 12 | 28 | 0 |
| 口碑 | 18 | 16 | 62 |
| 便利度 | 10 | 10 | 28 |

用户提到热量上限、蛋白质下限或低脂/高蛋白之类的标签时切到「营养优先」；
完全没提任何偏好时走「热门兜底」，此时口味、菜系、营养无从判断，全押口碑和便利度。

几个值得说明的处理：

- **用户没提的维度给中性分 0.5，不做惩罚。** 只说「想吃辣的」的用户不该因为没提预算被扣分。
- **评分做贝叶斯收缩。** 只有 20 人评的 4.9 分不该压过 800 人评的 4.6 分。
- **辣度算贴合度而非达标。** 能吃 4 级辣的人拿到 4 级辣的菜最满意，拿到不辣的菜虽然「能吃」但不是他想要的。
- **`budget_min` 只在这一层降权，不在过滤层拦截。** 用户说「想吃 15 块以上的」通常意思是「今天想吃好点」，把便宜菜全滤掉反而不合预期。
- **排序结果稳定可复现。** 并列时依次按销量、评分、菜品 id 兜底——顺序不稳定的推荐既没法调参也没法写断言。
- **同一窗口最多出 2 道菜。** 一次推荐全来自同一个窗口，分数再高体验也差。

## 本地运行

需要 Python 3.11+。

```bash
cd backend
python -m venv .venv
# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

pip install -r requirements.txt
pytest
```

## 配置千帆

复制 `backend/.env.example` 为 `backend/.env`，填入自己的密钥：

```
QIANFAN_AK=你的 API Key
QIANFAN_SK=你的 Secret Key
```

密钥在百度智能云控制台 → 千帆大模型平台 → 应用接入里创建应用后获取。
`.env` 已在 `.gitignore` 中，不会被提交。

**不配密钥也能启动**：`Settings.qianfan_configured()` 返回 False 时系统走纯规则模式，
少了自然语言偏好解析和大模型推荐语，硬性过滤与打分排序照常工作。

千帆客户端的容错分三层：单次请求 12 秒超时 → 最多重试 2 次（指数退避，只重试超时、
5xx 和限流类错误码）→ 连续失败 3 次触发熔断，60 秒内直接短路不再白等，
冷却结束自动放一个探测请求。客户端本身只抛 `QianfanError`，
降级成规则结果是上层 Agent 的职责，两边分开便于各自测试。

## 示例数据说明

`backend/app/data/dishes.json` 是按合理字段设计的模拟数据，覆盖了各种边界情况
（辣度 0–5、价格 1–22 元、素食/清真/低脂等标签、含过敏原的菜、以及一道停止供应的菜），
便于测试过滤逻辑。接入真实菜单时替换该文件即可，字段含义见 `app/models/dish.py`。
