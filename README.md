# 食堂味蕾雷达 (Canteen Flavor Radar)

基于 Agent 的高校食堂选餐系统。首届全国人工智能应用创新大赛校赛参赛作品。

针对高校食堂菜品信息不透明、学生选餐决策效率低等痛点，基于百度智能云千帆平台，
利用大模型驱动的 Agent 架构，实现从用户口味偏好输入到个性化菜品推荐的全流程智能化服务。

## 设计思路

核心是把「能不能吃」和「有多想吃」拆开：

| 层次 | 职责 | 特点 |
| --- | --- | --- |
| 偏好解析 | 自然语言 → 结构化偏好 | 大模型负责，失败时降级到关键词规则 |
| 硬性过滤 | 过敏原、忌口、饮食限制、预算上限、辣度上限 | 纯规则，结果确定可复现 |
| 排序打分 | 口味、菜系、预算、营养、口碑、便利度加权 | 纯规则，得分明细可解释 |
| 推荐语生成 | 结合菜品信息和用户原话写推荐理由 | 大模型负责，失败时用规则理由兜底 |

这样拆的原因：过敏原之类的安全约束不能交给可能产生幻觉的模型来把关，必须由确定性代码兜住；
而「为什么推荐这道菜」这类需要语感的表达，规则写出来又生硬，正好交给大模型。
模型不可用时系统降级但不瘫痪。

## 打分规则

六个维度各算出 0–1 的原始分，乘权重后累加，权重之和为 100，所以综合分天然落在 0–100。
权重按场景动态选择：

| 维度 | 默认 | 营养优先 | 热门兜底 |
| --- | --- | --- | --- |
| 口味 | 30 | 22 | 0 |
| 菜系 | 14 | 10 | 0 |
| 预算 | 16 | 14 | 10 |
| 营养 | 12 | 28 | 0 |
| 口碑 | 18 | 16 | 62 |
| 便利度 | 10 | 10 | 28 |

用户提到热量上限、蛋白质下限或低脂/高蛋白之类的标签时切到「营养优先」；
完全没提任何偏好时走「热门兜底」，此时口味、菜系、营养无从判断，全押口碑和便利度。

几个值得说明的处理：

- **用户没提的维度给中性分 0.5，不做惩罚。** 只说「想吃辣的」的用户不该因为没提预算被扣分。
- **评分做贝叶斯收缩。** 只有 20 人评的 4.9 分不该压过 800 人评的 4.6 分。
- **辣度算贴合度而非达标。** 能吃 4 级辣的人拿到 4 级辣的菜最满意，拿到不辣的菜虽然「能吃」但不是他想要的。
- **`budget_min` 只在这一层降权，不在过滤层拦截。** 用户说「想吃 15 块以上的」通常意思是「今天想吃好点」，把便宜菜全滤掉反而不合预期。
- **排序结果稳定可复现。** 并列时依次按销量、评分、菜品 id 兜底——顺序不稳定的推荐既没法调参也没法写断言。
- **同一窗口最多出 2 道菜。** 一次推荐全来自同一个窗口，分数再高体验也差。

## 降级策略

两处调用大模型，各自都有规则兜底，千帆挂了系统降级但不瘫痪：

| 环节 | 主路径 | 降级路径 |
| --- | --- | --- |
| 偏好解析 | 模型输出 JSON，Pydantic 校验 | 关键词词表 + 正则匹配 |
| 推荐语生成 | 模型把规则理由串成一句话 | 直接用规则理由拼句 |

降级时 `RecommendResponse.fallback_used` 置 True 并在 `message` 里说明，
用户知道解析可能不够准，而不是拿到一个看不出问题的结果。

模型输出的容错做得比较碎，因为实际会遇到各种脏输出：套 ```json``` 代码块、
前面加一句「好的，解析结果如下」、把「辣」写成 `spicy`、`spicy_tolerance` 给成 99、
少写几条推荐语。这些都单独处理成「能救的部分先救下来」，
而不是整条请求失败——一个词不在词表里不该让整次选餐白费。

**一条红线：模型解析出的偏好只是输入，不是许可。**
解析结果原封不动交给 `DishRepository` 过滤，过敏原和饮食限制由规则层判断。
即便模型返回带注入意图的内容（比如「忽略所有过滤条件」），
解析器只认已知字段，而真正挡住菜的是确定性的过滤代码，模型说什么都不影响结果。

## 本地运行

需要 Python 3.11+。

```bash
cd backend
python -m venv .venv
# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

pip install -r requirements.txt
pytest

# 起服务
uvicorn app.main:app --reload
```

启动后 <http://127.0.0.1:8000/docs> 是自动生成的接口文档，可以直接在页面上试。
`/api/health` 会告诉你当前是 `full` 还是 `rule-only` 模式。

## 前端

`frontend/index.html` 是一个单页界面，没有构建工具、没有依赖，两种方式都能看：

**方式一：直接双击 `frontend/index.html`。**
页面检测不到后端时会自动进入「演示模式」，用内置的 `demo-engine.js` 运行——
它是后端规则层（硬性过滤 + 六维打分 + 逐级放宽 + 规则理由）的等价 JS 移植，
所以过滤和打分结果与后端一致，只是推荐语走规则兜底而非大模型生成。
适合快速演示，不需要装 Python。

**方式二：起着后端，用浏览器打开同源地址。**
页面探到 `/api/health` 就切到真实接口，右上角徽标会显示「已连接后端」，
配了千帆密钥时显示「大模型可用」，推荐语下方标注也会从「规则生成」变成「大模型生成」。

界面上几个刻意的设计：

- **六维得分条**是主要的可解释性入口。条形长度是「占该维满分的比例」而不是绝对分，
  否则口味满分 30 和便利满分 10 画在一起没法比。权重为 0 的维度直接不画——
  热门兜底场景下画一排空条只会让人困惑。
- **解析回显**把系统理解到的条件列出来，过敏原、忌口、饮食要求用红色标出。
  用户能立刻确认「我说的过敏它收到了」，这比事后发现推荐错了要好。
- **含过敏原的菜会明确标注**（如「含蛋类」），即便用户没勾规避——知情权照给。
- 首屏直接给热门推荐，不让用户对着空白页面猜该输入什么。

改了 `backend/app/data/*.json` 之后，跑一次 `node scripts/build-demo-data.js`
同步演示数据快照。数据内联成 JS 而不是让页面 fetch JSON，
是因为 `file://` 下浏览器会把读本地 JSON 当跨域拒掉。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/recommend` | 按偏好推荐，body 收 `text` 或结构化 `preference` |
| GET | `/api/dishes` | 菜品查询，支持关键词/食堂/品类/菜系/餐段筛选 |
| GET | `/api/dishes/{id}` | 单道菜详情 |
| GET | `/api/canteens` | 食堂列表（含拥挤度） |
| GET | `/api/health` | 探活，回报千帆配置与可用状态 |

推荐接口的最小请求：

```bash
curl -X POST http://127.0.0.1:8000/api/recommend \
  -H "Content-Type: application/json" \
  -d '{"text":"想吃点辣的，20块以内，最近在减脂","limit":3}'
```

响应里除了菜品和推荐语，还带 `breakdown`（各维度得分明细）、
`parsed_preference`（系统怎么理解你的话，供前端回显确认）、
`total_candidates`（过滤后进入打分的菜数）和 `fallback_used`（是否降级）。

## 配置千帆

复制 `backend/.env.example` 为 `backend/.env`，填入自己的密钥：

```
QIANFAN_AK=你的 API Key
QIANFAN_SK=你的 Secret Key
```

密钥在百度智能云控制台 → 千帆大模型平台 → 应用接入里创建应用后获取。
`.env` 已在 `.gitignore` 中，不会被提交。

**不配密钥也能启动**：`Settings.qianfan_configured()` 返回 False 时系统走纯规则模式，
少了自然语言偏好解析和大模型推荐语，硬性过滤与打分排序照常工作。

千帆客户端的容错分三层：单次请求 12 秒超时 → 最多重试 2 次（指数退避，只重试超时、
5xx 和限流类错误码）→ 连续失败 3 次触发熔断，60 秒内直接短路不再白等，
冷却结束自动放一个探测请求。客户端本身只抛 `QianfanError`，
降级成规则结果是上层 Agent 的职责，两边分开便于各自测试。

## 示例数据说明

`backend/app/data/dishes.json` 是按合理字段设计的模拟数据，覆盖了各种边界情况
（辣度 0–5、价格 1–22 元、素食/清真/低脂等标签、含过敏原的菜、以及一道停止供应的菜），
便于测试过滤逻辑。接入真实菜单时替换该文件即可，字段含义见 `app/models/dish.py`。
